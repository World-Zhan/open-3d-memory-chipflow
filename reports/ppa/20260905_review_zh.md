# 2026-09-05 Croc PPA 与行业对照

SPDX-License-Identifier: Apache-2.0

**本轮完成寄生提取/SPEF 读回、CTS A/B 和定向分支 ECO：布线前 fanout 违规 200→4→0；最新 003 已修复八条新时钟网的 NDR 继承并通过独立结构连接校验。** 最新候选 active 面积 0.7208351136 mm²、TT 工具功耗 56.4 mW，slew/cap 仍为 71/135；电气、DRC、LVS 尚未闭环，当前不具备可流片状态。CTS/ECO 结果不能改写成最终布线 PPA 收益。

## CTS 同阶段 A/B：fanout 改善的 PPA 代价

[实验 JSON](croc-ppa-cts-ab-20260905-001.json)绑定 `croc-cts-fanout-ab-20260905-001` 的运行清单、源 placement ZIP、解包输入及两臂全部输出哈希。两臂使用同一 `02_croc.placed` checkpoint、容器、库、输入 SDC 和 15 pF IO 负载，仅修改 CTS 的 `sink_clustering_size`（默认→8）。两臂均完成 CTS、setup repair 与 detailed placement，使用 `estimate_parasitics -placement`；没有运行新布线。

| 同阶段指标 | Control（默认） | Candidate（8） | 观察与代价 |
|---|---:|---:|---|
| Fanout 违规 | **200** | **4** | 减少 196 个，尚未清零 |
| Slew / cap 违规 | **71 / 135** | **71 / 135** | 未改善 |
| Setup / hold 违规 | 0 / 0 | 0 / 0 | 现有 aggregate 报告保持，无完整 MMMC 证明 |
| Active area | 0.6855631776 mm² | 0.720646416 mm² | +0.0350832384 mm²（**+5.12%**） |
| Die / 物理 core | 3.671056 / 1.5710817024 mm² | 相同 | 边界未变，更多单元占用现有空间 |
| TT 工具总功耗 | **43.6 mW** | **56.3 mW** | +12.7 mW（**+29.13%**）；未有 workload 活动验证 |
| TT Clock 组功耗 | **7.63 mW** | **20.3 mW** | +12.67 mW；几乎解释全部总功耗增量 |

这是一项带明确 PPA 代价的电气改进候选，不能称为整体 PPA 优化。更细的 sink clustering 引入时钟网络面积和功耗成本；后续应研究剩余分支的定向修复以及更合适的 CTS 参数，而不是直接将此候选推广为最终实现。两个 CTS 总功耗数值与上节某个 RCX 数值恰好相同，也不表示它们属于同一分析阶段。

新候选仍需逻辑等价、合法布局与布线、路由后寄生/STA、严格 DRC/LVS 才能晋级。当前报告不把历史布局的失败数直接当作候选新布局的 DRC/LVS 结果，也不把“尚未运行”当作 PASS。

## 定向分支 ECO：fanout 清零，发现路由规则继承缺口

在 CTS candidate 的四个剩余 16-load 分支各插入两个 `sg13g2_buf_8`，每个缓冲器驱动 8 个原负载。`croc-cts-branch-eco-20260905-002` 使用 OpenDB 写新 ODB，再启动全新的 OpenROAD 进程执行 placement 和 STA；此前 `001` 尝试使用的 `insert_buffer` API 在固定容器中不可用，失败尝试不计为设计验证。

| 同阶段指标 | CTS candidate | 分支 ECO 002 | 差量 |
|---|---:|---:|---|
| Fanout 违规 | 4 | **0** | −4 |
| Slew / cap 违规 | 71 / 135 | **71 / 135** | 未改善 |
| Setup / hold 违规 | 0 / 0 | 0 / 0 | 现有 aggregate count 保持 |
| Active area | 0.720646416 mm² | **0.7208351136 mm²** | +188.6976 µm²（+0.026184%） |
| TT 工具总功耗 | 56.3 mW | **56.4 mW** | +0.1 mW；原始报告舍入精度内的工具估算增量 |

只读 DEF 审查发现一项需要在布线前修复的遗漏：四条 parent 输出网在 ECO 前后均带 `NONDEFAULTRULE CTS_NDR_1`，而新增八条 `eco_cts_b*_g*` 网络只有 `USE CLOCK`，没有 NDR。`CTS_NDR_1` 对 Metal2–5 设置 WIDTH=200、SPACING=420 DBU；新网没有自动继承这些非默认路由要求。保留 CLOCK 类型和满足 fanout，并不能证明保留原 CTS 路由策略。

002 因 NDR 缺失未晋级，原始记录保持不变。随后在独立 003 中修复继承并补充结构校验，结果见下一节。002 的 source/output 哈希、逐分支 NDR 审查与同阶段差量仍保留于 [ECO 002 JSON](croc-ppa-cts-branch-eco-20260905-002.json)。

[独立结构验证](../../runs/croc-cts-branch-eco-20260905-003/structural_validation.json)证明：折叠八个新增非反相 buffer 后，原有网络连接保持一致；新增 buffer 的 VDD/VSS 显式连接、die 边界和原 NDR 几何定义保持。验证记录绑定源/目标 DEF 哈希，最新 [PPA JSON](croc-ppa-cts-branch-eco-20260905-003.json)再绑定该验证文件与 manifest 全部源/输出哈希。该检查没有证明完整形式等价、时钟波形行为、路由后时序或 DRC/LVS 签核。

003 与历史 002 的 `cts_branch_eco.rpt` 字节哈希完全一致，面积、功耗和违规数也相同。它证明在此次 placement 寄生估计中数值未变化，不能据此推断 NDR 修复对实际布线、电容、串扰或功耗没有代价。后续仍须合法布线、路由后 RCX/STA，以及严格 DRC/LVS；目前仅将 003 作为保留原路由规则的后续实验输入。

## 对下一轮的具体指导

1. **电气先闭环**：在保持 IO 负载和库限制的前提下，研究 CTS fanout/电容/转换时间。每个 A/B 使用同 checkpoint 与同分析阶段；路由后重新做提取验证。
2. **DRC/LVS 保持严格根因路径**：不能把提取时序成功当成 DRC/LVS PASS；叶单元、父层、整芯片应分别有独立证据。
3. **功耗补真实活动**：工作负载、仿真时间窗、SAIF/VCD 覆盖率、时钟门控状态及内存访问比例是必需输入。此前仅能报告工具估算。
4. **性能补可复现软件基准**：固定编译器/参数和存储等待周期运行 CoreMark 或明确的 MCU 工作负载，再与 Ibex 的 CoreMark/MHz 比较。当前不从相近 ISA 猜测分数。
